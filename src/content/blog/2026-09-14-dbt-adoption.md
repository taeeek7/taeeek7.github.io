## 들어가며

처음에는 데이터를 안정적으로 가져오는 데 집중했습니다.  Airflow로 반복 작업을 자동화하고, Kafka CDC로 운영 DB를 BigQuery에 복제하면서 분석에 필요한 데이터를 하나씩 확보해왔습니다.

데이터가 쌓이자 운영팀이 시트나 Redash에서 보는 숫자의 계산 기준을 관리하기 어려워졌습니다. SQL은 BigQuery 뷰, 예약 쿼리, Airflow DAG, Redash에 나뉘어 있었고, 기준 하나를 바꾸려면 관련 SQL과 사용처를 찾아 함께 확인해야 했습니다.

이 과정을 정리하기 위해 dbt를 도입했습니다. SQL, 모델 간 의존성, 테스트, 설명을 한 프로젝트에서 관리하고, 기존 Airflow 실행 흐름에 연결하는 것이 이번 작업의 목표였습니다.

고객사 업무 요청 데이터를 첫 모델로 만들고 테스트 서버에서 실행해봤습니다.

## 1. 왜 dbt가 필요했을까?

열한시는 공간 관리 플랫폼을 운영합니다. 운영팀은 일감, 배정, 클레임, 정산 데이터를 주로 커넥티드 시트와 Redash에서 확인합니다. 이 사용자들이 데이터로 업무를 처리하려면 조회 대상과 계산 기준이 분명해야 합니다.

예를 들어 일감 하나에 여러 배정과 여러 클레임이 연결될 수 있습니다. 이를 그대로 조인하면 행 수가 늘어나면서 일감 금액까지 반복 집계될 수 있습니다. 날짜 경계, NULL 처리, 상태별 포함 조건도 결과에 영향을 줍니다.

이런 규칙이 조회별로 흩어지면 SQL을 수정할 때마다 같은 내용을 다시 검토하게 됩니다. 일부 SQL과 Python 테스트는 이미 코드로 관리하고 있었으므로, 다음 단계는 이들을 일관된 변경 흐름으로 연결하는 일이었습니다.

필요한 기능은 크게 세 가지였습니다.

- 정의 관리: 업무 계산을 SQL 모델로 관리하고 공통 로직을 재사용하기
- 변경 검증: 모델 변경 시 계산과 실제 데이터의 품질을 확인하기
- 맥락 제공: 원천, 의존 관계, 컬럼 의미를 모델과 함께 설명하기

dbt는 이 기능들을 SQL 중심의 프로젝트 안에서 연결할 수 있었습니다. 기존 Airflow와 함께 사용하면 실행·재시도·알림 체계도 이어갈 수 있어, 첫 도입 구조로 선택했습니다.

## 2. 모델 설계의 출발점은 사용자의 조회 목적

모델 설계는 운영팀이 조회할 결과부터 정하는 것으로 시작했습니다. 원천 테이블 구조를 모두 이해해야 조회할 수 있는 환경보다, 목적에 맞는 모델을 선택하고 기간과 지점을 필터링하는 환경을 만들고 싶었습니다.

이를 위해 내부 정제·공통 모델과 공식 공개 모델의 역할을 나눴습니다.

```text
업무 원장 · 서버 로그 · GA
          ↓
내부 정제·공통 모델
타입, 시간대, 중복, 공통 계산 정리
          ↓
공식 공개 모델
일감 상세, 일별 운영 현황 등 조회 목적에 맞는 결과
          ↓
커넥티드 시트 · Redash
```

세 원천을 활용하는 구조는 도입 전체의 방향이며, 첫 구현은 고객사 업무 요청 모델에 집중했습니다.

모델별로는 한 행의 의미, 키, 포함 대상, 계산 기준을 먼저 정의하도록 했습니다. 기간이나 지점만 바뀌는 요청은 같은 모델의 필터로 처리하고, 상세 내역과 일별 집계처럼 행 단위가 바뀌면 별도 모델로 구성하는 방식입니다.

공통 모델도 첫 사용 사례에 필요한 범위부터 만듭니다. 이후 여러 모델에서 같은 계산이 반복되면 공통 계층으로 옮겨 재사용하도록 방향을 잡았습니다. 이렇게 하면 실제 수요를 확인하면서 모델을 확장할 수 있습니다.

## 3. Airflow는 실행을, dbt는 변환을 담당한다

기존 DAG에는 원천 조회, 컬럼별 타입 정의, MERGE SQL, 검증이 함께 들어 있었습니다. dbt 도입 과정에서는 각 도구의 책임을 다음처럼 정리했습니다.

| 구성 | 담당 역할 |
| --- | --- |
| 원천 복제 | MySQL 등의 데이터를 BigQuery로 가져오기 |
| dbt | SQL 변환, 모델 의존성, 데이터 검사, 모델·컬럼 설명 |
| Airflow | 실행 날짜, 태스크 순서, 재시도, 실패 알림 |
| Cosmos | dbt 모델과 테스트를 Airflow 태스크로 구성하기 |

`kube-airflow/dbt/`에 공용 프로젝트를 두고, 각 DAG가 필요한 모델을 선택해 실행하도록 했습니다. 모델을 한곳에서 관리하면 여러 DAG가 같은 정의를 공유할 수 있습니다.

프로젝트 구조는 다음과 같습니다.

```text
dbt/
└── models/
    ├── staging/       원천을 모델에서 사용하기 위한 정리
    ├── intermediate/  재사용할 중간 변환과 공통 계산
    └── marts/         사용 목적에 맞는 최종 모델
```

단순한 변환은 staging에서 mart로 바로 연결합니다. BigQuery 데이터셋은 사용자와 접근 권한을 기준으로 설계하므로, 코드의 폴더 구조와 데이터셋을 각각의 목적에 맞게 구성할 수 있습니다.

실행 환경에서는 Airflow 이미지에 Cosmos를 설치하고, dbt Core와 BigQuery 어댑터는 별도 가상환경에 두었습니다. 의존성을 분리한 만큼 설치 확인도 각 환경의 `pip check`, import, 버전 검사로 진행했습니다. 로컬 Compose에서는 DAG 14개가 로드되고 import 오류가 0건인 것을 확인한 뒤 모델 구현으로 넘어갔습니다.

## 4. 첫 모델: 고객사 업무 요청 적재

첫 파일럿으로는 고객사 업무 요청 데이터를 선택했습니다. 기존 적재 DAG를 바탕으로 컬럼 변환, 증분 반영, 검증을 dbt로 옮겨볼 수 있는 대상이었습니다. 하나의 모델을 끝까지 연결해보면 이후 모델을 추가할 때 사용할 기준도 정리할 수 있습니다.

실행 흐름은 다음과 같습니다.

```text
MySQL의 지정 날짜 데이터
  → BigQuery raw 교체
  → 원천 검사
  → staging view
  → id 기준 mart MERGE
  → 결과 검사
```

원천 복제 함수는 MySQL 메타데이터에서 컬럼과 타입을 읽어 raw 스키마를 구성합니다. DB 간 전송에 필요한 타입 매핑은 복제 함수가 처리하고, 업무에 필요한 컬럼 선택과 변환은 dbt SQL에 둡니다.

staging 모델에서 컬럼을 선택하고 변환하는 부분입니다.

```sql
select
    id,
    insert_at,
    cast(check_in_claim as string) as check_in_claim,
    datetime(_airflow_loaded_at, 'Asia/Seoul') as loaded_at
from {{ source('raw', 'raw_client_request_list') }}
```

위 예시는 설명을 위해 컬럼을 줄였습니다. `source()`는 원천을, `ref()`는 다른 모델을 참조합니다. 이 참조를 통해 원천부터 최종 모델까지의 의존 관계를 표현합니다.

raw에는 이번 날짜의 입력을 담고, 최종 mart에는 데이터를 누적합니다. mart의 증분 설정은 다음과 같습니다.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='id',
    full_refresh=false,
    on_schema_change='fail'
) }}
```

`id`가 같으면 기존 행을 갱신하고, 새로운 id는 추가합니다. 같은 날짜를 다시 실행할 때도 이 키를 기준으로 반영하므로 재실행에 따른 중복을 제어할 수 있습니다. 스키마가 달라지면 실행을 실패시켜 변경 내용을 확인하도록 했습니다.

## 5. Cosmos 연동에서 만난 DAG 파싱 문제

Airflow와 연결하는 과정에서는 scheduler의 DAG 파싱이 병목이 됐습니다. 모델 목록을 가져오기 위해 `dbt ls`를 실행하는 방식에서 파싱 시간 초과가 발생했습니다.

해결 방법은 모델 정보가 담긴 manifest를 미리 생성하고, Cosmos가 이 파일을 읽어 태스크를 구성하게 하는 것이었습니다. scheduler는 준비된 그래프를 읽고, 모델 실행과 검사는 각 태스크에서 수행합니다.

manifest를 사용하면 모델 수정과 그래프 갱신을 함께 관리해야 합니다. SQL이나 YAML을 변경한 뒤 manifest가 이전 상태로 남으면 실행 그래프가 코드와 어긋날 수 있기 때문입니다.

그래서 PR에서 DB 인증 없이 프로젝트를 파싱하고, 모델 정의가 바뀌면 manifest를 기능 브랜치에 자동 커밋하도록 구성했습니다. 생성 시각 같은 실행별 메타데이터는 비교에서 제외해 의미 있는 변경만 남기도록 했습니다.

검증도 두 단계로 나뉩니다. manifest 생성은 프로젝트 파싱과 그래프 구성을 확인하고, 실제 BigQuery 실행은 SQL과 데이터 검사의 동작을 확인합니다.

## 6. 테스트 서버에서 확인한 결과

검증은 실행 환경, DAG 구성, 실제 데이터 순으로 진행했습니다. 구현 중 단위 테스트 47개를 통과했고, 이후 TaskGroup·날짜 파라미터·알림·CI 변경은 로컬 실행과 각 변경에 대한 확인으로 이어갔습니다. 47개라는 수치는 그 앞선 구현 단계의 결과입니다.

로컬 Airflow에서는 manifest 기반 DAG 로딩, 모델별 태스크 구성, raw·staging·mart 생성을 확인했습니다. GitHub Actions에서도 manifest 생성과 bot 커밋이 정상적으로 수행됐습니다.

테스트 서버에서는 `target_date=2026-09-30`으로 실행했습니다. 실행 시각은 10월 1일 18:49~18:52 KST였으며 결과는 다음과 같습니다.

| 단계 | 결과 |
| --- | --- |
| MySQL → raw 복제 | 19건 |
| raw 검사 | id NOT NULL·UNIQUE, insert_at NOT NULL — 3개 PASS |
| mart 반영 | MERGE 19건 |
| 결과 검사 | id NOT NULL·UNIQUE, insert_at NOT NULL — 3개 PASS |
| 동일 날짜 재실행 | 로컬에서 처리한 날짜를 다시 실행해 id 중복 검사 통과 |

배치 운영에서는 실패 복구나 과거 데이터 반영을 위해 같은 날짜를 다시 처리할 일이 생깁니다. 이번 검증에서는 원천 준비부터 MERGE와 결과 검사까지의 흐름이 테스트 서버에서 동작하고, 재실행 후에도 id 유일성이 유지되는 것을 확인했습니다.

첫 모델의 dbt 검사는 실제 데이터의 필수 값과 키 유일성을 확인하는 data test 여섯 개입니다. 앞으로 계산이 복잡한 모델에는 고정 입력과 기대 결과를 사용하는 unit test를 추가해 조인 중복, NULL, 상태 분기, 날짜 경계까지 검증할 계획입니다.

## 7. 품질 검증 다음에는 공개 정책이 필요

파일럿을 구현하면서 함께 고민한 부분은 검사 실패 후의 동작입니다. 현재 mart 검사는 MERGE 이후에 실행하므로, 결과 검사에서 실패하면 해당 실행에서 반영한 데이터가 테이블에 남습니다.

운영팀에 공식 모델을 제공하려면 이 동작까지 설계해야 합니다. 모델별로 필수 검사와 공개 조건을 정하고, 실패했을 때 이전 통과 결과를 유지할지, 갱신을 중단할지, 품질 경고를 제공할지 결정해야 합니다. 실시간 뷰에는 마지막 검증 시각과 데이터 갱신 시점을 함께 안내할 필요도 있습니다.

원천 반영 방식도 모델 특성에 맞게 확장해야 합니다. 현재 파일럿은 생성일 기준으로 조회하므로 과거 행의 수정은 해당 생성일을 재실행해 반영합니다. 원천 삭제의 전파와 날짜별 전체 데이터를 메모리에 읽는 방식의 처리량은 추가 검토 항목입니다.

이번 작업으로 SQL과 테스트, 설명을 공용 프로젝트에 두고 Airflow에서 모델별 실행 결과를 확인하는 기반을 만들었습니다. 다음 단계는 실제 사용하는 시트와 Redash 쿼리를 기준으로 모델을 확장하고, 기존 결과와 키·행 수·금액·일자별 집계를 대조하는 일입니다.

첫 모델은 테스트 서버에서 실행해봤지만, 운영팀에 공개하려면 검사 실패 시 처리와 기존 집계 결과 대조가 더 필요합니다. 이 조건을 정리하면서 공식 모델을 하나씩 늘려가려고 합니다.
