매달 지점 수십 개의 정산을 한다. 담당자가 어드민에서 엑셀을 수동으로 내려받아 작업하고 있길래, 구글 시트의 **커넥티드 시트** 기능으로 BigQuery를 직접 조회하게 바꿨다. 시트에서 지점과 기간을 고르면 쿼리가 그대로 나가는 구조다. ([Kafka CDC로 운영 DB를 복제해둔](/blog/2025-09-10-kafka-cdc/) replica 테이블을 그대로 쓴다.)

동작은 잘 됐다. 그런데 스캔량을 보고 멈칫했다. **새로고침 한 번에 2.9GB.**

담당자는 지점을 바꿔가며 새로고침한다. 수십 개를 훑으면 어떻게 되는지는 계산해볼 필요도 없었다.

## 큰 테이블이 문제겠지

쿼리가 참조하는 테이블이 15개였다. 크기 순으로 줄을 세웠다.

```
record_tbl     1,272 MB   수백만 행
work_tbl         975 MB   백만 행대
schedule_tbl     882 MB   백만 행대
assign_tbl       147 MB   수십만 행
... 나머지 11개는 전부 10MB 미만
```

위의 셋 중 하나겠거니 했다. 특히 `record_tbl`은 일감 단가 이력이 쌓이는 가장 큰 테이블이라 유력해 보였다.

그래서 이 테이블들을 제일 많이 쓰는 **일감 시트 뷰**를 물리 테이블로 구웠다. 파티션도 걸고 클러스터링도 걸고.

```sql
CREATE OR REPLACE TABLE mart.work_sheet
PARTITION BY resolved_date
CLUSTER BY workspace_id, group_id
AS SELECT * FROM views.work_sheet
```

**1,614MB → 890MB.** 절반.

기대치와 한참 달랐다. 이상한 건, 구워진 테이블을 직접 조회하면 76MB밖에 안 나온다는 거였다. 그런데 전체 쿼리는 890MB다. 어딘가에서 800MB가 새고 있었다.

## 하나씩 떼어보기

쿼리는 일감 시트에 클레임과 장기객실 정보를 조인하는 구조였다. 각 조각을 따로 dry-run 해봤다.

| 조각 | 단독 스캔 |
|---|---|
| 일감 시트 (물리화 후) | 76 MB |
| 클레임 뷰 | 160 MB |
| **장기객실 뷰** | **817 MB** |

`long_stay_record`. 결과가 **8천 행**짜리, "이 일감이 장기 투숙 건인가"를 표시하려고 붙인 부가 정보용 작은 뷰. 크기 순위를 볼 때 아예 후보에도 안 올렸던 쪽이다.

게다가 이 뷰는 두 군데에서 쓰이고 있었다. 일감 쿼리에서 한 번, 장기객실 전용 시트에서 또 한 번. **새로고침마다 1.6GB씩 두 번** 나가고 있었던 셈이다.

## 8천 행이 817MB인 이유

뷰 정의를 열었다.

```sql
FROM `replica.schedule_tbl` rs
WHERE rs.pms_hotel_type = 'PMS_A'
  AND JSON_VALUE(rs.pms_data, '$.isLongStay') = 'true'
```

`pms_data`는 PMS(호텔 예약 시스템)에서 받아온 예약 정보를 통째로 담은 **JSON 문자열 컬럼**이다. 그리고 하필 "장기 투숙인가"를 판정하는 `isLongStay` 플래그가 그 JSON **안에** 있었다.

BigQuery는 컬럼 기반 저장소다. 필요한 컬럼만 읽는 게 강점인데, 여기선 그게 작동하지 않는다. `isLongStay`가 true인 행을 고르려면 **일단 모든 행의 `pms_data`를 읽어서 파싱해야** 하기 때문이다. 컬럼 프루닝도 파티션 프루닝도 원리적으로 불가능하다. 파싱이 끝나야 어떤 행이 필요한지 알 수 있으니까.

조건을 하나씩 붙여가며 재봤다.

```sql
-- 컬럼 하나로만 필터
SELECT COUNT(*) FROM schedule_tbl
WHERE pms_hotel_type = 'PMS_A';
--> 7 MB

-- JSON 안을 들여다보는 조건 추가
SELECT COUNT(*) FROM schedule_tbl
WHERE pms_hotel_type = 'PMS_A'
  AND JSON_VALUE(pms_data, '$.isLongStay') = 'true';
--> 578 MB
```

**7MB에서 578MB.** 조건 한 줄 추가에 82배다. 같은 테이블, 결과 행수도 비슷한데.

이게 이번에 제일 크게 배운 거다. **스캔량을 정하는 건 테이블 크기가 아니라 필터가 프루닝을 태우느냐다.** 882MB짜리 `schedule_tbl`은 어떻게 거르느냐에 따라 7MB일 수도 578MB일 수도 있다. 크기 순으로 테이블을 줄 세우고 위에서부터 의심한 게 처음부터 틀린 접근이었다.

## 고치기

원인을 알고 나니 답은 단순했다. 세 뷰를 전부 물리 테이블로 굽는다.

```
mart.work_sheet       백만 행대 / 544 MB
mart.claim_sheet      만 행대   / 3.8 MB
mart.long_stay_sheet  8천 행대  / 1.46 MB   ← 885MB 스캔이 여기로 접힘
```

장기객실은 파티션도 클러스터링도 안 걸었다. 8천 행짜리에 그런 걸 걸면 메타데이터 오버헤드가 이득보다 크다.

| 쿼리 | 전 | 후 |
|---|---|---|
| 일감 + 클레임 + 장기 | 1,614 MB | 71 MB |
| 장기객실 | 1,156 MB | 15 MB |
| 클레임 | 211 MB | 0 MB |
| **합계** | **2,981 MB** | **86 MB** |

35배. 클레임이 0MB로 찍히는 건 물리화 후 원본이 3.8MB까지 줄어든 데다, dry-run이 스캔 바이트를 0으로 보고하는 경로를 탔기 때문이다. 정확히 어느 쪽인지는 끝까지 확인하지 않았다.

## 스캔은 35배인데 속도는 4배

여기서 예상이 또 빗나갔다. 스캔이 35배 줄었으니 응답도 그만큼 빨라질 줄 알았다.

| 쿼리 | 전 | 후 |
|---|---|---|
| 일감 | 16.0s | 3.6s |
| 장기객실 | 10.7s | 2.1s |
| 클레임 | 5.1s | 3.3s |
| **합계** | **31.8s** | **9.0s** |

4배. 나쁘지 않지만 35배와는 거리가 멀다.

이유는 클레임 행을 보면 드러난다. **스캔이 사실상 0인데 3.3초가 걸린다.** BigQuery는 쿼리마다 잡 생성·스케줄링·슬롯 할당에 고정으로 1~2초를 쓴다. 스캔을 아무리 줄여도 이 아래로는 안 내려간다.

바닥에 닿았다는 뜻이다. 여기서 쿼리를 더 쥐어짜도 사용자 체감은 안 바뀐다. 최적화를 **언제 멈춰야 하는지** 알려주는 신호이기도 했다.

## 비용은 사실 푼돈이었다

정직하게 적어두면, 이 작업의 비용 절감 효과는 없다시피 했다.

on-demand $6.25/TB 기준, 월 1회 정산에 새로고침 6번을 가정하면:

| | 전 | 후 |
|---|---|---|
| 월 비용 | $0.112 | **$0.016** |

월 11센트가 1.6센트가 됐다. 연간으로 쳐도 $1.34 → $0.19다. 비용만 보면 안 하는 게 맞는 작업이었다.

가치는 전부 다른 데 있었다. **지점 하나당 32초 대기와 9초 대기는 작업 흐름 자체가 다르다.** 10곳을 훑으면 5분 20초가 1분 30초가 된다.

처음에 "스캔량이 크다"를 문제로 잡았던 게 사실 프레이밍 실수였다. 진짜 문제는 "느리다"였고, 스캔량은 원인 중 하나였을 뿐이다. 다행히 원인이 겹쳐서 결과적으로 맞는 데를 고쳤지만, 목표를 잘못 잡았으면 스캔량만 열심히 줄이고 체감은 그대로인 결말도 가능했다.

## 대가로 내준 것

물리 테이블은 자동으로 갱신되지 않는다. 이전엔 CDC 지연 9분이 곧 신선도였는데, 이제는 **마지막으로 구운 시점**이 신선도다.

굽는 비용은 2,131MB에 40초. 손익분기는 새로고침 7~8회다. 지점을 바꿔가며 보는 패턴이니 첫 회차부터 이득이다.

이 경우엔 신선도를 내주는 게 오히려 나았다. 정산은 마감된 기간을 정리하는 작업이라 **작업 도중에 데이터가 바뀌지 않는 편이 낫다.** 실시간성이 필요 없는 정도가 아니라, 없는 게 나은 케이스였다.

## 접은 시도들

기록해둘 만한 실패들.

**조인 순서 재배치, CTE 통합** — 읽은 레코드가 9.08억에서 9.24억으로 *늘었다*. 옵티마이저를 사람이 이겨보려던 대가.

**뷰에 클러스터링** — 뷰는 저장 실체가 없으니 원리상 불가능하다. 해보고 알았다.

**조인 키에 클러스터링** — `work_tbl`에 `CLUSTER BY room_id`를 걸었는데 프루닝이 전혀 안 됐다. 클러스터링은 `WHERE`에 상수가 주어질 때 작동하지, 조인을 경유해서 값이 결정되면 소용없다. `WHERE room_id IN ('상수', ...)`로 직접 주면 0MB까지 떨어지는데, 시트에서 그렇게 쓸 수는 없었다.

**Materialized View** — 일감 쿼리는 소스 테이블이 14개라 생성 자체가 안 됐다(제한 10개). 클레임 쪽은 만들어졌지만 `max_staleness`가 필수인데, 그 창을 벗어나면 원본을 다시 읽어서 84MB 밑으로 안 내려갔다.

**안 쓰는 컬럼 제거** — 스캔은 0.6% 줄었다. 슬롯은 16% 줄었지만 스캔 과금에는 거의 영향이 없었다.

유효했던 건 결국 한 가지 패턴뿐이다. **큰 테이블 조인을 통째로 걷어내기.** 클레임 뷰에서 안 쓰는 단가 6종을 지웠더니 조인 두 개가 통째로 빠지면서 1,090MB가 221MB가 됐고, 장기객실 물리화도 같은 원리였다. 부분 최적화는 전부 한 자릿수 퍼센트에 그쳤다.

## 검증은 행수만 보면 안 된다

물리 테이블과 원본 뷰를 이렇게 비교했다.

- ID 집합의 **양방향 차집합** — 행이 빠지거나 늘었는지
- 같은 ID끼리 **내용 해시** — 값이 달라졌는지

일감 33,745행 / 장기 5,261건 / 클레임 323건 전부 ID 집합이 정확히 일치했다. 내용 해시에서 5행이 달랐는데, 확인해보니 구운 뒤 40분 사이에 들어온 CDC 갱신분이었다. 로직 차이가 아니라 신선도 차이라 다시 구우면 사라진다.

행수만 봤으면 "33,745 = 33,745, 통과"로 넘겼을 거다. **행수는 같은데 값이 다른** 케이스는 해시까지 봐야 잡힌다.

## 배운 것

**크기 순으로 의심하면 틀린다.** 882MB 테이블도 조건에 따라 7MB이고, 8천 행짜리 뷰도 817MB일 수 있다. 테이블 크기가 아니라 **프루닝이 되느냐**가 스캔량을 정한다.

**JSON 컬럼 안에서 필터하지 마라.** 필터에 쓸 키는 JSON 밖으로 꺼내 별도 컬럼으로 두고 클러스터링을 건다. 이번 건의 근본 원인이었고, 스키마를 짤 때 미리 갈랐어야 할 문제였다.

**스캔량과 응답 시간은 비례하지 않는다.** 쿼리당 고정 오버헤드 1~2초에 닿으면 거기가 바닥이다. 스캔이 사실상 0인 쿼리가 3.3초 걸리는 걸 보고서야 최적화를 멈췄다.

**비용이 목표인지 속도가 목표인지 먼저 정하라.** 이번엔 비용은 푼돈이었고 속도가 전부였다. 프레이밍을 잘못 잡으면 열심히 엉뚱한 걸 줄인다.

## 남은 것

**굽는 걸 깜빡하면 낡은 데이터로 정산하게 된다.** 이게 이번 변경의 진짜 비용이다. 이전 구조에선 시트를 열면 9분 전 데이터가 보장됐는데, 이제는 사람이 버튼을 눌러야 최신이 된다. 콘솔에 공유 쿼리로 등록해두고 정산 시작 전 실행하는 절차로 정리했지만, 절차는 잊힌다. 언젠가 "왜 어제 완료한 일감이 안 보이지"로 돌아올 여지가 있다.

**물리 테이블은 콘솔에서 쿼리문이 안 보인다.** 뷰는 "세부정보" 탭에 정의가 그대로 뜨는데, 테이블은 저장된 데이터일 뿐이라 어떤 SQL로 만들어졌는지 흔적이 없다. 나중에 볼 사람이 출처를 찾을 방법이 없어서, 테이블 설명란에 원본 뷰 경로와 갱신 방법을 두 줄로 박아뒀다. 뷰를 물리화할 때 같이 해야 하는 일인데 이번에 처음 알았다.

그리고 근본적으로는 **`isLongStay` 플래그가 JSON 안에 있는 게 문제**지 물리화가 해결책은 아니다. CDC 적재 단계에서 이 플래그를 별도 컬럼으로 빼면 뷰 그대로도 7MB에서 끝난다. 지금은 적재 스키마를 건드리기 부담스러워 우회했지만, 이건 해결이 아니라 미룬 것에 가깝다.
