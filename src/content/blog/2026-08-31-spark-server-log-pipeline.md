## 들어가며

열한시에서는 Kafka를 통해 애플리케이션 로그를 GCS에 JSON.gz로 보관하고, Airflow에서 pandas/PyArrow로 Parquet을 만들어 BigQuery 외부 테이블로 조회하고 있었습니다.

이 구조를 운영하다 보니 정해야 할 처리 규칙이 늘어났습니다. 새로운 필드를 어떻게 반영할지, 잘못된 로그를 어떻게 추적할지, 같은 날짜를 다시 처리할 때 중복을 어떻게 제어할지 같은 문제들입니다. 파일별 변환으로 남는 작은 파일과 외부 테이블의 조회 성능도 개선 대상으로 보고 있었습니다.

Spark로 로그를 정제하고 오류를 분리한 뒤 BigQuery 네이티브 테이블에 적재하도록 바꿨습니다. 표본으로 처리 규칙을 정하고, 로컬 PoC와 Dataproc 실데이터 실행을 거쳐 Airflow에 연결했습니다.

## 1. 로그 처리 구조를 다시 살펴본 계기

8월에는 기존 로그 변환 태스크가 한 시간 만에 타임아웃 난 일이 있었습니다. 파일 4,297개 중 4,281번째를 처리하던 시점이었습니다.

스택트레이스 끝에는 GCP 인증 키 검증인 `RSA_check_key`가 나타났습니다. 앞선 파일들이 같은 인증정보로 처리됐고, 실행 시간이 설정된 `execution_timeout`과 일치한다는 점을 바탕으로 배치의 처리 과정을 살펴봤습니다.

파일마다 GCS 클라이언트를 새로 생성하면서 인증을 반복하고 있었습니다. 배치 호출부에서 만든 클라이언트를 하위 함수에 넘겨 재사용하도록 수정하고, 불필요한 API 호출과 서비스 간 순차 의존도 정리했습니다.

파일 하나를 처리하는 방식이 전체 배치 시간에도 영향을 주고 있었습니다. 이후 로그 처리를 다시 설계하면서 형식 검증, 오류 보존, 재처리와 분석용 적재도 함께 다루기로 했습니다.

Spark 도입에는 분산 batch를 실무 데이터로 경험하고 검증하려는 목적도 있었습니다. 첫 단계의 평가 기준은 데이터 처리의 정확성과 재실행 동작으로 잡았고, 성능과 비용은 이후 비교 실험에서 확인할 항목으로 두었습니다.

## 2. Raw 수집부터 분석 테이블까지

Raw 수집은 기존 Kafka와 GCS Sink가 담당하도록 유지했습니다. 원본을 남겨두면 변환 로직을 수정한 뒤 과거 데이터를 다시 처리할 수 있고, 수집과 처리 단계의 문제도 각각 추적할 수 있습니다.

전체 흐름은 다음과 같습니다.

```text
Server → Kafka → GCS Raw JSONL.gz
                      ↓
               Dataproc Spark batch
                 ├─ 정상 → Curated Parquet → BigQuery native table
                 └─ 변환 실패 → DLQ Parquet

Airflow: 날짜·설정 준비 → Spark 제출 → 완료 확인 → BigQuery 적재
```

Spark 코드는 `keeper-spark` 저장소의 `jobs/server_log`에 두었습니다. Job 안에서 파싱, 변환, 품질 검사, Parquet 저장을 처리합니다. Airflow는 실행 날짜와 인자, 원격 작업 상태, BigQuery 적재와 알림을 관리합니다. 실제 데이터는 GCS와 Dataproc, BigQuery 사이에서 이동합니다.

실행 환경으로 선택한 Dataproc Serverless는 batch 단위로 Spark를 실행할 수 있어 초기 운영 부담을 줄일 수 있었습니다. executor는 2개로 제한하고 TTL은 30분으로 설정했습니다. 세 서비스를 하나의 batch에서 처리해 실행 환경의 최소 비용을 공유하도록 했으며, 현재 서비스별 처리는 Python 루프에서 순차로 진행합니다.

Curated Parquet은 변환과 적재 사이의 확인 지점입니다. 저장 결과를 직접 검증할 수 있고, BigQuery 적재 실패 시 어떤 단계에서 문제가 발생했는지 구분하기도 쉽습니다. 최종 조회에는 BigQuery 네이티브 테이블을 사용하도록 구성했습니다.

## 3. 표본을 확인하며 정한 스키마

처음 계획을 작성할 때는 로그 안에 JSON 문자열이 들어 있는 구조를 가정했습니다. 공통 필드를 추출하고 나머지를 `attributes`로 보존하는 방안도 검토했습니다.

표본을 확인하니 Raw는 중첩 없는 문자열 컬럼의 gzip JSONL이었습니다. 기존 BigQuery 외부 테이블에도 컬럼이 나뉘어 있었고, 추가로 필요한 `keeperId` 같은 필드를 함께 반영할 수 있었습니다.

이 결과를 바탕으로 원본 키와 값을 유지하고, 시간 필드에 명시적인 타입을 부여하는 방향으로 설계를 정리했습니다.

| 항목 | 처리 규칙 |
| --- | --- |
| 일반 원본 필드 | STRING/null, 원본 이름과 값 유지 |
| 빈 문자열·없는 키 | 빈 문자열 유지, 없는 키는 NULL |
| timestamp | UTC TIMESTAMP로 변환 |
| log_date | timestamp에서 계산한 KST DATE |
| keeperId·staffId | 원본에 있으면 적재 |
| 새 문자열 키 | 정상 행의 추가 컬럼으로 반영 |
| 처리 메타데이터 | service, source_file, processed_at, run_id 추가 |

원본 필드의 의미를 보존하는 것을 중요하게 봤습니다. 예를 들어 빈 문자열과 없는 키는 입력에서 표현하는 상태가 다르므로 각각 빈 문자열과 NULL로 유지합니다. 타입 불일치나 키 충돌은 실패 사유와 함께 기록해 원본을 다시 확인할 수 있게 했습니다.

## 4. 변환 실패는 DLQ에 보존한다

JSON 파손, timestamp 누락·변환 실패, 비문자열 값, 중복 JSON 키, 메타데이터 키 충돌 등은 DLQ로 분리합니다. DLQ에는 다음 정보를 저장합니다.

```text
raw_payload, source_file, error_reason,
service, run_id, processed_at
```

원문과 출처, 실패 사유가 함께 있으므로 어떤 입력이 어떤 규칙에서 실패했는지 추적할 수 있습니다. 정상 행은 처리를 이어가고, 결과를 다음 식으로 대조합니다.

```text
Raw 건수 = Curated 건수 + DLQ 건수
```

여기서 `level=ERROR`인 애플리케이션 로그는 형식이 유효하면 Curated로 적재합니다. 서비스 오류를 분석하려면 ERROR 로그도 조회 대상에 포함되어야 하기 때문입니다. DLQ는 파이프라인의 변환 규칙을 통과하기 어려운 레코드를 다루는 경로입니다.

파일 읽기 자체가 실패하는 경우에는 Job을 실패시킵니다. 읽을 수 있는 개별 행의 형식 오류와, 입력을 온전히 읽을 수 없는 상황에 각각 맞는 동작을 적용했습니다.

## 5. 날짜 설계: 수집일과 발생일을 구분하기

날짜는 재처리와 파티션 적재의 기준이므로 먼저 의미를 정리해야 했습니다. GCS 폴더는 KST 수집일을 기준으로 구성되어 있고, 로그의 timestamp는 UTC 발생 시각입니다.

입력 폴더를 고르는 값은 `target_date`, 행마다 계산하는 발생일은 `log_date`로 사용했습니다. 예를 들어 UTC `2026-09-26 15:10:00`은 KST로 9월 27일이므로 해당 행의 `log_date`는 `2026-09-27`입니다.

Spark는 timestamp에서 발생일을 계산하고, 폴더 날짜와 일치하지 않는 행 수를 집계합니다. timestamp가 없거나 변환에 실패하면 DLQ로 보내 발생일을 확인할 수 있도록 했습니다.

최종 BigQuery 적재는 선택한 날짜의 파티션을 교체하므로, 모든 행의 log_date가 적재 날짜와 일치해야 한다는 조건을 적용했습니다. 날짜 불일치가 발생하면 로드가 실패합니다. 향후 지연 도착 데이터를 처리할 때는 해당 발생일의 기존 데이터를 포함해 재구성하는 정책이 필요합니다.

정기 실행은 매일 03:00 KST이며, Airflow 실행 구간 종료일을 기준으로 전날 폴더를 선택합니다. 이 기준을 사용하면 실행이 지연돼도 같은 날짜를 처리할 수 있습니다. 수동 실행은 처리 날짜를 명시하도록 했습니다.

## 6. 재실행 전략: 실행별 출력과 날짜별 교체

Spark의 출력은 run별로 분리했습니다.

```text
curated/_runs/<run_id>/service=<service>/source_date=<date>/
dlq/_runs/<run_id>/service=<service>/source_date=<date>/
```

같은 경로가 이미 있으면 저장을 실패시켜 기존 결과를 보호합니다. 같은 Airflow DAG run의 재시도는 동일 Dataproc Batch ID로 기존 작업에 연결하고, 새 Spark 실행에는 새 DAG run을 사용합니다.

소비 단계에서는 성공한 run의 결과를 지정합니다. 동일 날짜를 여러 번 처리하면 같은 원본의 출력이 여러 경로에 존재할 수 있고, 일부 서비스의 처리 후 Job이 실패하면 중간 출력도 남을 수 있습니다. 따라서 batch 성공 상태와 출력 경로를 함께 확인해야 합니다.

BigQuery는 `log_date` 일별 파티션과 `service` 클러스터링으로 구성했습니다. 적재 시 선택한 날짜 파티션을 `WRITE_TRUNCATE`로 교체합니다.

초기에는 서비스 × 로그 일자 단위의 교체를 생각했지만, 최종 구현에서는 전체 서비스 결과를 날짜 파티션 하나에 적재하는 방식으로 정리했습니다. 그에 맞춰 실행 조건도 설정했습니다. batch 서비스의 결과만으로 파티션을 교체하면 keeper와 indicator 데이터도 함께 사라질 수 있기 때문입니다.

그래서 BigQuery 적재는 전체 서비스를 선택한 실행에서 허용하고, 일부 서비스 선택은 변환 검증용으로 사용하도록 했습니다. 중복을 막는 것과 별개로, 재실행할 때 교체할 데이터 범위도 정해야 했습니다.

## 7. 로컬 PoC와 GCS 커넥터 호환성 확인

로컬 PoC는 Python 3.11, Java 17, PySpark 3.5.3의 `local[2]`에서 시작했습니다. 9월 17일 batch 표본 파일 세 개로 입력 39건, 정상 39건, DLQ 0건을 확인했습니다. Parquet을 저장한 뒤 다시 읽어 건수를 비교했습니다.

실패 경로는 합성 데이터로 검증했습니다. JSON 파손, KST 날짜 경계, 타입 불일치, 빈 문자열과 NULL, 새로운 키, 전체 DLQ, 반복 실행 등을 포함해 테스트 12개를 통과했습니다. 반복 실행의 내용 비교에서는 실행마다 바뀌는 `run_id`와 `processed_at`을 제외했습니다.

이후 GCS를 직접 읽는 노트북 검증에서 커넥터 호환 문제를 만났습니다. 클래스 로드와 인증 토큰 발급까지 성공했지만, `count()`로 읽기를 실행하자 `Options$OpenFileOptions` 클래스 누락 오류가 발생했습니다.

로컬 PySpark에 포함된 Hadoop은 3.3.4였고, 처음 사용한 GCS 커넥터 3.1.18은 Hadoop 3.3.6을 대상으로 빌드된 버전이었습니다. 필요한 클래스가 로컬 JAR에 없는 것을 확인한 뒤, 로컬 커넥터를 Hadoop 3용 2.2.33으로 교체하고 인증 설정도 해당 버전에 맞게 수정했습니다.

교체 후에는 같은 GCS 파일의 `count()` 31건과 첫 세 행 읽기를 확인했습니다. 로컬 커넥터 수정은 개발 환경에 적용했으며, Dataproc에서는 런타임에 포함된 커넥터를 사용합니다.

클래스 로드와 인증만 확인하고 끝냈다면 놓쳤을 오류였습니다. 실제 읽기를 실행하는 action까지 확인해야 했습니다.

## 8. Dataproc 실데이터 실행과 Airflow 연동 검증

Dataproc Runtime 2.3에서는 9월 27일 batch 로그를 처리했습니다.

| 항목 | 결과 |
| --- | --- |
| 입력 파일 | 4,263개 |
| Raw | 215,063건 |
| Curated | 215,063건 |
| DLQ | 0건 |
| 수집일·발생일 불일치 | 0건 |
| 저장 후 검증 | Parquet 재조회 건수 일치 |

저장 전에는 정상·DLQ 분류 건수를 대조하고, 저장 후에는 Parquet을 다시 읽어 비교했습니다. 실제 데이터 실행은 정상 경로와 완전성 검증의 근거로, 합성 테스트는 오류 처리의 근거로 사용했습니다.

Airflow 연동에서는 단위 테스트 40개와 실제 Airflow/Provider 기반 mock 테스트 16개를 통과했습니다. 날짜 경계, 동일 run의 재시도 ID, batch 상태, 적재 조건과 알림을 확인했습니다.

로컬 Airflow에서는 실제 Dataproc 변환, BigQuery 적재, Slack 알림까지 연결해 실행했습니다. 9월 29일 데이터를 대상으로 확인한 서비스별 결과는 다음과 같습니다.

| 서비스 | Curated | DLQ |
| --- | --- | --- |
| batch | 162,300행 | 0행 |
| keeper | 1,758행 | 0행 |
| indicator | 756행 | 0행 |

Spark의 저장 검증과 BigQuery Load Job 완료를 확인했고, 최종 테이블에 별도 COUNT 쿼리를 실행해 대조하는 검증은 추가 항목으로 남았습니다. PR 시점에는 테스트 서버의 정기 실행도 배포 후 확인할 단계였습니다.

## 9. 다음 단계: 처리량과 조회 성능 측정

첫 구현에서는 서비스별 정상·DLQ 결과를 각각 `coalesce(1)`로 저장합니다. 초기에는 출력 파일 수를 단순하게 관리할 수 있지만, 데이터가 늘어나면 쓰기 병렬성이 제한될 수 있습니다. 처리량에 맞춰 파티션 수와 출력 파일 크기를 조정해야 합니다.

다음에는 셔플과 스큐, executor 메모리와 spill, AQE의 영향을 비교하고, 기존 외부 테이블과 네이티브 테이블의 대표 쿼리 실행 시간·스캔량을 측정하려고 합니다. 이번에 확인한 행 수와 테스트 결과는 처리 정확성의 근거이며, 성능과 비용의 개선 폭은 이 비교를 통해 평가할 예정입니다.

Raw를 보존하고 변환 실패를 따로 남기면서, 실행별 결과와 날짜별 재적재를 추적할 수 있게 됐습니다. 실제 로그를 넣어보니 엔진을 연결하는 일 외에도 빈 값의 의미, 날짜 경계, 실패 후 다시 실행할 범위를 하나씩 정해야 했습니다.
