n8n 월 실행 한도를 넘겼다는 알림을 받았다. 워크플로우가 수십 개 도는데 어디서 새는지 몰라 실행 이력을 정렬해봤더니, 범인이 깔끔하게 하나였다. 슬랙 메시지를 받아서 용도별 봇으로 분배하는 라우터 하나. **7일간 3,000건, 월 환산 약 13,000건.** 이 워크플로우 혼자 한도의 대부분을 먹고 있었다.

이상한 건, 이 라우터가 실제로 하는 일은 그렇게 많지 않다는 거였다. 하루에 몇 건 라우팅하는 게 전부인데 실행 건수만 만 단위다. 뭔가 앞뒤가 안 맞았다.

## 필터는 이미 있었다

라우터의 Slack Trigger는 워크스페이스 전체를 구독하고 있었다. 봇이 들어가 있는 **모든 채널의 모든 메시지**가 실행을 만든다. 그리고 첫 노드가 대부분을 버린다.

```js
// 사람의 일반 대화는 버리고, 이 봇을 멘션한 메시지만 다음 단계로
if (isHuman && !isMentioned) continue;
```

필터가 없어서 생긴 문제가 아니었다. 필터는 처음부터 잘 동작하고 있었다. 문제는 **이 코드가 실행이 시작된 다음에 돈다**는 것이다. 99%를 버려도 과금은 이미 끝난 뒤다.

실행 이력 600건을 분류해봤다.

| 분류 | 건수 | 비중 |
|---|---|---|
| 봇이 채널에 올린 메시지 | 265 | 44.2% |
| `message_changed` / `message_deleted` | 159 | 26.5% |
| 사람 일반대화 | 163 | 27.2% |
| **실제 라우팅된 건** | **13** | **2.2%** |

**필요한 13건을 잡으려고 600건을 실행하고 있었다.**

여기서 짐작이 하나 깨졌다. 나는 사람들 잡담이 범인일 거라고 생각하고 있었다. 실제로는 27%였고, 진짜 덩치는 봇 메시지(44%)와 메시지 수정 이벤트(26%)였다. 누가 메시지를 올렸다 고치면 `message_changed`가 또 날아온다는 걸 그제야 실감했다. 추정만으로 손댔으면 엉뚱한 데를 고치고 "왜 안 줄지?" 했을 거다.

## 안 되는 길을 네 번 걸었다

원인은 명확한데 해법이 안 나왔다. 시도했다가 접은 것들을 남겨둔다. 대부분의 시간이 여기 들어갔다.

**멘션 트리거로 바꾸기.** "멘션 온 것만 받으면 되잖아" 싶었다. 그런데 라우팅 대상의 대부분이 외부 시스템 봇이 채널에 올리는 **일반 메시지**다. 멘션이 아니라서 이 경로가 통째로 죽는다. 게다가 실측해보니 7일간 사람이 이 봇을 멘션한 건 **0건**이었다. 줄일 대상도 아니었던 걸 줄이려던 셈이다.

**트리거 노드의 무시 목록 쓰기.** Slack Trigger에 "무시할 사용자 ID" 옵션이 있다. 이름만 보면 봇도 걸릴 것 같았다. 확신이 안 서서 노드 소스를 열어봤다.

```ts
if (userIds.includes(req.body.event.user ?? req.body.event.message?.user)) {
  return {};
}
```

`event.user`만 본다. 그리고 **`bot_id`는 이 파일 466줄 어디에도 등장하지 않는다.** 봇 메시지는 `user` 필드가 없으니 `undefined`가 되고, `includes(undefined)`는 언제나 false다. 낭비의 44%인 봇 메시지를 이걸로는 한 건도 못 거른다. `subtype`도 검사하지 않으니 26%인 수정 이벤트도 마찬가지.

소스를 안 봤으면 무시 목록에 봇 ID를 수십 개 채워 넣고 왜 그대로인지 한참 헤맸을 것이다. **옵션 이름은 계약이 아니다.**

**채널 단위로 구독 범위 좁히기.** 채널 ID 필드가 값을 하나만 받는 구조라 노드 하나당 채널 하나다. 대상 채널이 스물몇 개니 트리거 노드도 스물몇 개. 게다가 n8n은 Slack에 채널별 구독을 따로 등록하지 않아서(등록 훅이 사실상 빈 함수다) 노드 24개가 각자 전체 이벤트를 받아 각자 거른다. 관리 비용만 늘고 이득이 없다.

**Slack 워크플로우 빌더로 중계하기.** "슬랙에서 봇 메시지를 감지해서 n8n 웹훅을 호출하면 되지 않나." 두 군데서 막혔다. 우선 아웃바운드 HTTP 스텝이 없다 — "From a webhook"은 외부에서 슬랙으로 들어오는 인바운드다. 그리고 애초에 봇 메시지로는 트리거가 안 될 가능성이 높았다. 공식 문서에 이렇게 적혀 있다. *"The `message_posted` event filters out both messages by apps (to prevent recursive replies)."*

가장 깨끗한 해법은 소스 시스템에서 슬랙을 거치지 않고 직접 웹훅을 쏘는 것이었는데, 그 시스템이 우리 소유가 아니라 손댈 수 없었다.

## 필터를 과금 바깥으로

네 번 막히고 나서야 문제를 다시 읽었다. 나는 계속 **n8n 안에서** 거를 방법을 찾고 있었다. 그런데 진짜 문제는 필터의 성능이 아니라 **위치**였다. 필터가 과금 경계 안쪽에 있는 한, n8n 안에서 뭘 해도 실행은 이미 만들어진 뒤다.

그러면 답은 하나다. **n8n 앞에 프록시를 두고 거기서 거른다.**

```
전:  Slack ──[모든 메시지]──────────→ n8n Slack Trigger   → 13,000건/월
후:  Slack ──[모든 메시지]──→ Lambda ─[필요분만]─→ n8n     →    280건/월
```

AWS Lambda Function URL, 파이썬 89줄. 핵심은 이게 전부다.

```python
bot_id = ev.get("bot_id") or (ev.get("bot_profile") or {}).get("id")
if bot_id:
    return bot_id in ALLOWED_BOT_IDS, f"...:bot={bot_id}"

if any(m in (ev.get("text") or "") for m in MENTIONS):
    return True, "pass:mention"
return False, "drop:human"
```

몇 달을 고민한 것치고 로직이 허무할 만큼 단순하다. 애초에 어려운 문제가 아니었고, 어려웠던 건 이걸 **어디에 둘 것인가**였다.

### 설계에서 신경 쓴 세 가지

**n8n을 한 줄도 안 건드린다.** 서명 검증을 n8n에 그대로 남겼다. Signing Secret이 Lambda로 넘어오지 않으니 비밀이 사는 곳이 늘지 않는다. 대신 조건이 붙는다 — body를 **재직렬화하면 안 된다.** 공백 한 글자만 바뀌어도 `X-Slack-Signature` 검증이 깨지므로 원본 바이트를 그대로 흘려보낸다.

이 선택의 진짜 값어치는 롤백이다. Lambda가 이상하면 **Slack 앱의 Request URL 한 줄을 되돌리면** 원래 구조로 돌아간다. n8n 쪽에 아무 흔적이 없으니까.

**전달에 실패해도 200을 반환한다.** 처음엔 본능적으로 500을 뱉게 짜뒀다가 고쳤다. Slack은 2xx가 아니거나 3초를 넘기면 최대 3회 재시도하고, **그 재시도가 n8n 실행을 또 만든다.** 실패할 때 정직하게 500을 반환하면, 줄이려던 실행이 오히려 4배가 된다. 에러를 숨기는 게 아니라 재시도 증폭을 막는 것이라, 대신 로그와 알람으로 본다.

**`url_verification`은 Lambda가 직접 답한다.** 이건 실패해보고 알았다. 처음엔 이 요청도 그냥 n8n으로 넘겼는데 계속 `challenge_failed`가 났다. n8n의 응답이 Slack까지 되돌아가는 경로가 없어서였다. URL 등록 핸드셰이크는 프록시 계층의 일이지 n8n이 관여할 이유가 없다.

## 결과

실행 이력 600건을 필터에 그대로 재생해봤다.

| | 건수 | 비중 |
|---|---|---|
| 통과 | 13 | 2.2% |
| 차단 | 587 | **97.8%** |

| | 전 | 후 |
|---|---|---|
| 월 실행 | ~13,000건 | **~280건** |

Lambda 비용은 프리 티어(월 100만 요청) 안이라 0원이다. 한도 초과로 유료 플랜을 올리는 대신, 요금이 안 붙는 자리로 필터를 옮긴 셈이 됐다.

## 함정 기록

두 개는 남겨둘 만하다. 둘 다 "설정이 잘못됐나" 하고 멀쩡한 데를 한참 뒤지게 만들었다.

**Slack Trigger의 웹훅 경로는 `/webhook/<webhookId>/webhook`이다.** 끝이 중복돼 보이지만 오타가 아니다. 앞은 웹훅 ID고, 뒤의 `webhook`은 노드에 하드코딩된 경로다. 일반 Webhook 노드는 이 중복이 없어서 더 헷갈린다. 이걸 모르고 404를 한참 봤다.

**Request URL 변경은 즉시 반영되지 않는다.** Verified가 뜨고 Save까지 눌렀는데도 실제 전송 경로가 바뀌는 데 10~20분 걸렸다. 그 사이에 나는 코드가 잘못된 줄 알고 멀쩡한 Lambda를 계속 뜯어보고 있었다.

## 배운 것

**필터가 과금 경계의 어느 쪽에 있는지가 전부다.** 같은 조건으로 같은 걸 거르는데, 위치를 한 뼘 옮겼더니 비용이 1/46이 됐다. 조건문 한 줄도 안 바뀌었다. 성능이나 로직을 손대기 전에, 이 코드가 **무엇의 안쪽에서 도는지** 먼저 보는 게 맞았다.

**옵션 이름 대신 소스를 읽어야 할 때가 있다.** "무시할 사용자 ID"는 이름만 보면 봇도 걸릴 것 같지만 `bot_id`는 쳐다보지도 않는다. 문서가 거짓말을 한 건 아니고, 내가 이름에서 기대를 만들어낸 거다. 이번엔 소스를 열어본 덕에 하루를 벌었다.

**"이걸로 줄겠지" 추정 대신 실행 이력을 뜯어봐야 한다.** 나는 사람 잡담을 범인으로 지목했는데 실제로는 27%였고, 멘션 경로는 아예 사용 0건이었다. 분포를 안 보고 손댔으면 없는 트래픽을 줄이느라 바빴을 것이다.

## 남은 것

**Lambda가 단일 장애점으로 하나 늘었다.** 이게 이번 변경의 진짜 비용이다. n8n의 에러 알림은 *실행 중에 난* 에러만 잡으므로, Lambda가 죽어서 이벤트가 **아예 안 들어오는** 상황은 조용히 지나간다. 실행 건수를 줄인 대가로, 실행이 0건인 게 정상인지 장애인지 구분할 수 없는 구간을 만든 셈이다. 호출 수 0건과 에러율에 CloudWatch 알람을 걸어둘 것.

[예전에 커넥터가 RUNNING이라고 우기면서 아무것도 안 하고 있었던 일](/blog/2026-07-14-kafka-connector-offset-loss/)을 겪고 나서 생긴 습관인데, 조용한 실패는 항상 이런 식으로 새 구조에 따라 들어온다. 뭔가를 줄였으면, 그게 0이 됐을 때 누가 알려주는지도 같이 정해야 한다.

그리고 구조적으로는 여전히 "다른 시스템의 봇이 채널에 올린 메시지를 엿듣는" 형태다. 소스 쪽에서 웹훅을 열어주면 Slack Trigger 자체가 없어진다. 지금은 그럴 수 없어서 이렇게 두지만, 이건 해결이 아니라 우회다.
